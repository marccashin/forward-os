# FORWARD OS — Claude Working Rules

## Deployment workflow (ALWAYS follow this order)

1. Make changes on a feature branch (never directly on `main` or `staging`)
2. Push feature branch to GitHub
3. Merge feature branch → `staging` first
4. Marc tests on staging
5. Only after Marc approves: merge to `main` via pull request

**Never push to `main` directly. GitHub ruleset enforces this, but follow it regardless.**
**Never skip staging. Even small fixes go to staging first.**

## One change at a time

- One session ships to a repo at a time. Check for open PRs and other sessions' branches before starting.
- Do not open a PR while the backend system check (`GET /api/smoke-test/status` on the Railway backend) or the PR check on GitHub is red. Fix the red check first.
- After a backend merge, wait for the deploy and read the system check again before starting the next change.

## Security rules

- Never paste GitHub tokens in chat — they are auto-revoked by GitHub the moment they appear in a conversation
- Never commit `.env` files or secrets to the repo

## Data rules

- Everything is stored globally in Supabase so any device can access it at any time
- `localStorage` is only used as a fast display cache — Supabase is always the source of truth
- When writing to `property_notes`, do NOT include a `created_by` field — that column does not exist
- A listing note (`property_notes`) is saved with `supaRest.saveNote(propertyId, subfolder, content)`, which calls the database function `save_property_note` (SQL in `sql/2026-10-03_save_property_note.sql`, run by Marc Oct 3, 2026). It replaces the note in one step. Never delete a note and then insert it: if the insert fails the note is gone. Never call the backend's `/save-property-note` from the app. Voice notes (`voice_note`) are the exception: many per listing, added with a plain insert, and the function refuses them.
- Every saved version of a listing note is kept in `property_note_history` (SQL in `sql/2026-10-05_property_note_history.sql`, run by Marc Oct 5, 2026). The DATABASE writes it, by a trigger on `property_notes`, in the same step as the save; the app can only read it and must never try to write, change or delete a row. `supaRest.saveNote()` calls `save_property_note_by`, which is `save_property_note` plus the signed-in agent's name. Not kept: voice notes, the description writer's chat (`listing_remarks_chat`) and `campaign_sections`, which autosave constantly. On the listing, `lstHistFor(type)` lists the earlier versions and `lstHistCurrent(type)` says when and by whom the one on screen was saved. If history cannot be loaded, say so on screen (`lstHistError`). The lists are shown for the net sheet, CMA, description, MLS Data, Seller Prep Guide and the campaign letter (the last three since Oct 13, 2026). The letter autosaves while the agent types, so every pause can add a version.
- Read listing notes newest first (`order=updated_at.desc.nullslast`) and use the first row of each type.
- CMA comp fees: the subject's monthly fee is HOA fee plus condo fee, and a comp's HOA/Mo box must hold the same sum. A BLANK comp fee means not known yet and gets NO HOA adjustment in `recalcAll()`; a typed 0 means the comp has no fee and is adjusted in full (Marc, Oct 4, 2026; before that a blank counted as $0 and put the subject's whole fee times the multiplier on every comp of a condo CMA, $86,500 each). So a fee box must show a stored 0 as 0 and store an emptied box as blank, never as 0. The import fills the fee; a closed sale left blank is orange until a number is typed (a click does not clear it). Direction (Marc, Oct 4, 2026): a fee is a cost to the buyer, so a comp with a HIGHER fee than the subject is adjusted UP and a lower fee DOWN: `(comp fee - subject fee) x multiplier`.
- CMA comp garages (Marc, Oct 6, 2026): a BLANK Garage box on a closed sale means not known yet and gets NO parking adjustment in `recalcAll()`; a typed 0 means no garage and is adjusted in full. Same rule as the fee box: the Garage box must show a stored 0 as 0 and store an emptied box as blank. A closed sale left blank is orange until a number is typed (a click does not clear it). A garage count above 4 is orange until the agent presses Confirm or types another number (`garageOdd`, `c._garageOk`). A red notice (`updateAdjWarning`) names any closed sale whose total adjustment is more than 15% of its sale price. The check and the notice are display only. They came from the audit of Oct 6, 2026: 57 saved comps matched an independent calculator on every line, and the huge adjustments were a 32 and an 8 typed in the garage box.
- The listing's own parking is read from its MLS Data line by `fosParkingFromMls()` in `index.html` (top level, outside setup()). Never decide a garage from the words attached or detached alone, and never take the first number in the line as the count: "2 car garage and 8 car driveway" opened as Street / None with 2 spaces (1926 Ruxton Rd). When the line does not settle the answer the prefill carries `parkingUnsure` and the builder marks Parking Type CHECK THIS on a new CMA. A saved CMA keeps what was saved.
- CMA condition grades (Marc, Oct 5 and 6, 2026): a CMA started on or after Oct 6, 2026 values condition as a PERCENT of each comp's sale price against a standard home, on the appraisers' scale: A+ = C1 (+16%), A = C2 (+8%), B = C3 the standard home (0), C = C4 (-9%), D = C5 or C6 (-18%). Effect on a comp: `comp price x (1 + listing %) / (1 + comp %) - comp price` (`calcCondAdj`, `CMA_GRADES` in `cma-tool.html`). The percents are fixed in code and come from 37,080 appraisals in FORWARD's counties (project doc OPEN-condition-grade-study-2026-10-05); there is no box to change them. The listing and new rows start on B. The key must be on screen before a grade is picked, and on the client's PDF with its source note. **A CMA saved before that date is never touched**: it keeps the flat dollar grades (A+ 15,000 to D -10,000, C the ordinary home), its letters and its old key. The method is saved with the draft (`gradeMethod`: `pct1` or `flat`; a draft with no marker and at least one property is `flat`). Never convert one into the other, and never change what a `flat` CMA prints.
- Earlier versions of a CMA live in `cma_snapshots` (SQL in `sql/2026-10-06_cma_snapshots.sql`): a copy of the whole draft, added when a PDF goes out, before Reset / New CMA, before an earlier version is opened, and before an agent's edit of a teammate's newer CMA replaces their own older draft. The app adds and reads rows and must never change or delete one. Autosaves are not kept. Reset / New CMA from a listing deletes nothing: it keeps a copy, starts from the listing's prefill with no comps, and stamps the draft `startedFresh` so a teammate's OLDER draft does not reopen over it.
- A listing's PDFs are stored in the Supabase Storage bucket `listing-files` (private, PDF only, 20MB; the app's role can add and read, never change or delete; SQL run by Marc Oct 6, 2026), at `<listing id>/<kind>/<UTC time><3 random>__<agent>__<name>.pdf`. `fosListingFiles` in `index.html` is the only way the OS files, lists and opens them; `cma-tool.html` has its own copy of the path and upload functions (`_listingPdfPath`, `_listingPdfPut`) and the two must stay the same. Every save is a NEW file: never upsert, never reuse a name. `_doSaveToPropertyDrive` files a tool's own PDF there whether or not the listing has Drive folders (most do not, and nothing creates them); a save with text only files no PDF. The CMA Builder's Save to Listing files the CMA PDF the same way and never posts to `web-production-d9b04`. The listing page lists them newest first (`lstPdfFor`, `lstPdfOpen`); if the list cannot be loaded it says so (`lstPdfError`). Not covered yet: the pick-a-listing save window and the buyer-side tools, which still use Drive only.
- The agent chooses the comps (Marc, Oct 6, 2026). The builder holds 6 closed sales, 10 pending, 10 active. When an import has more ticked than a section has room for, the review window says so and adds NOTHING until the agent unticks enough (`impCount`, `impRefresh` in `cma-tool.html`). Never drop the overflow in file order, never rank or pick comps for the agent: the PDF says the agent selected them. The window shows each property's sold date, price, size, beds and baths and distance so the choice is informed. While the sheets are read, the progress panel guesses the wait from the files' total size (about 30 seconds per MB, `progGuessSeconds` in `cma-tool.html`; a 16-property Bright file is about 4 MB and 2 minutes), says it up front, and past the guess says Still reading and keep the page open. Never guess from the number of files: one file can hold 16 properties.
- A listing's address is split for the builder by `fosSplitListingAddress()` in `index.html` (top level). A tail that is only a state goes to State, never to City ("1415 Riverside Ave. Baltimore, MD" used to give City = MD). When the city had to be read off the end of the street part, the prefill carries `addressUnsure` and the builder marks Address and City CHECK THIS on a new CMA.
- CMA wording (Marc, Oct 4, 2026): the number beside each comp is the **Indicated Value**, what that sale says the listing is worth. Never label it Adjusted Price or Adj Price, and never describe a comp as inferior or superior: say the listing is better (plus) or the comp is better (minus). The internal names (`_adj.adjusted`, `c0_adjPrice`) are unchanged.
- CMA drafts (`cma_sessions`, one row per agent and listing): the builder OPENS the newest draft for the listing that has at least one property in it, whoever saved it (Marc, Oct 3, 2026). It always SAVES under the signed-in agent's own name. Never let an empty draft win over one with properties, and never save before the load has finished.
- The seller net sheet has ONE calculation, `nsCompute()` (Oct 5, 2026). `calcNetSheet()` (the Calculate button) and `nsRecalcSilent()` (the PDF step) both call it and hold no math. Never put a rate, fee or tax rule anywhere else. A change to the math must keep `ci/net-sheet-numbers-test.js` passing: the executed KVS Title and Universal Title figures can never move, and any of the 116 recorded sheets in `ci/net-sheet-golden.json` that a deliberate rule change moves must be re-recorded in the same PR, with the reason in the PR.
- The seller net sheet PDF (`nsGeneratePDFDoc`, layout of Oct 11, 2026, Marc) prints the lines in three groups: Charges Paid by Seller with a total, Credits to Seller with a total, and a Settlement Summary (sale price, mortgage payoff, charges, credits) ending in Net Proceeds to the Seller. The loan payoff is shown beside the sale price at the top and is not a charge. **There is no Gross Equity line (Marc removed it).** The page holds no rate, fee or tax rule: `nsSheetGroups()` only sorts the lines `nsCompute()` returned (negative amount = credit, a line labelled `1st Loan Payoff` or `2nd Loan Payoff` = payoff, the rest = charge), and the net in the navy bar is `ns.result`. So a new kind of line needs no PDF change unless it is a payoff, and renaming the two loan labels needs `nsSheetGroups()` changed with it. **The sale price printed is the price the sheet was calculated for** (net plus payoff plus charges less credits, in cents), never the form's box: Save to Listing and Download with no closing date draw the PDF without calculating again, and a price changed after Calculate must not print above lines worked out for the old one. Never read `ns.salePrice` in the PDF code. The seller's name prints only on a sheet opened from a listing, from that listing's own record (`nsSheetSeller()`); the standalone sheet has none. A later page carries a one-line heading with the address. The saved text note and the form are unchanged.
- A listing's market (`properties.market`) is free text and is not always the code: the oldest listings say "Maryland", and Follow Up Boss names states in full. Read it for its meaning ONLY through `fosMarketCode()` (top level in `index.html`), which turns DC / MD / VA and their full names (Maryland, Virginia, District of Columbia, Washington, DC) into the code and anything else into '' (Marc, Oct 12, 2026: "This cannot happen"; 211 Arbor Vista Ln, market "Maryland", opened its net sheet as DC). Never compare `market` to 'DC', 'MD' or 'VA' directly. A listing with no recognised market shows "Set state" on its badge, never DC. The backend creates a Follow Up Boss listing with FUB's Market, else the state its address names as a whole word, else none (forward-os-backend `fub_market.py`); a CMA started by voice with no state gets none (DC is where the builder values driveways).
- No net sheet without a full address, and no default state (Marc, Oct 12, 2026: "they cannot run a net sheet without a full address"). `nsAddressCheck()` in `index.html` is asked first by `calcNetSheet()`, `nsDownloadPDF()` and `nsSaveToProperty()` (through `nsAddressOk()`), in both net sheet forms. It refuses unless the address box has a street number and name, a city, a state and a 5-digit ZIP; refuses a state outside DC, Maryland and Virginia; refuses when the state picker (`ns.jurisdiction`) is in another state; and, on a sheet opened from a listing, refuses when the listing's badge (`fosMarketCode(market)`) is blank or another state. The reason shows in red above Calculate (`nsAddrProblem`). Never add a way to make or save a net sheet that skips it, and never let any form or listing default to DC: the New Listing window's Market starts empty, follows the State box, and refuses to create a listing when the two disagree. Tests give their sheets a full address in the sheet's own state; the address is not part of the math.
- Every listing opens its own tools (Marc, Oct 5, 2026). `lstOpenProperty()` closes any open tool panel and clears a net sheet that belongs to another listing; a caller that wants a panel open sets `lstToolOpen` AFTER calling it. The in-listing net sheet fills from that listing only: address and unit from the listing, HOA fee and sale price (the List Price, only a plain dollar figure) from its MLS Data note, and only into an empty box. The standalone net sheet never shows a form stamped with a listing (`ns._propId`). Any new in-listing tool whose form lives in a shared object must be cleared in `lstOpenProperty()`.
- The Seller Prep Guide belongs to one listing (Oct 13, 2026). `sellerPrepSFH` and `sellerPrepCondo` are shared lists, so `sellerPrepLoadFor(owner, savedText)` rebuilds them from the standard copies (`_sellerPrepDefaults`) every time the owner changes: `lstOpenProperty()` loads the listing's saved `seller_prep` note, `lstOpenTool('sellerprep')` reloads when the lists were last used elsewhere, and `lpOpen('sellerprep')` (Just Listed) always starts standard. A saved checklist is read back by `sellerPrepParseSaved()`, which reads only the exact text `sellerPrepBuildTextSummary()` writes; anything else (text rewritten in the campaign editor) shows the standard list and says so (`sellerPrepLoadNote`), never a guess. Change the writer and the reader together. Unsaved changes do not survive opening another listing, on purpose.
- Approve for marketing (Oct 9, 2026): a listing description is approved when a row for the listing exists in `listing_description_approvals` (SQL in `sql/2026-10-09_listing_description_approvals.sql`). **The Command Center reads this table, so its four columns (`property_id`, `content`, `approved_by`, `approved_at`) are a fixed contract: never rename, retype or add meaning to them without asking Marc.** One row per listing; row exists = approved, row deleted = not approved, re-approval replaces the row. The app can only READ the table. An approval is written by the database function `approve_listing_description(p_property_id, p_content, p_approved_by)`, which freezes the saved text and refuses when the saved text is not the text the agent was reading. An approval is removed only by the DATABASE: a trigger on `property_notes` deletes the row when the listing's saved `listing_remarks` no longer holds exactly the approved text, whichever save path wrote it. Saving identical text keeps it. So the app must never try to insert, change or delete a row, and must never decide for itself that an approval was cleared: after a save it asks the database (`lstApprAfterSave`) and shows the answer. Show "Approved" only through `lstApprIsOn()` (a row the database returned whose text is exactly the text on screen); a failed read is shown as a failed read, never as Approved or Not approved. Any new place that saves `listing_remarks` must go through `supaRest.saveNote()`, which fires the `fos-note-saved` event the recheck listens for.
- Approve for marketing covers TWO texts (Oct 9, 2026, SQL in `sql/2026-10-09_listing_description_flyer_pdf.sql`): the description and a flyer version of 200 words at most. The flyer version is a listing note, `property_notes` subfolder `listing_flyer`, saved with `supaRest.saveNote()` like any other; on screen it lives in `lstFlyer.text`, not in `lstNotes`. Two nullable columns were added to `listing_description_approvals` and are part of the Command Center's fixed contract: `flyer_content` (the approved flyer version) and `pdf_url` (public https address of the branded PDF). A row approved before that keeps both null and covers the description only. The app approves through `approve_listing_description_with_flyer(p_property_id, p_content, p_flyer_content, p_approved_by)`, which refuses unless BOTH texts are exactly the saved ones and the flyer is 200 words or fewer. The database's clearing rule covers both: saving different text in EITHER note deletes the row. Words are counted the same way in the app (`fosWordCount`) and the database (`listing_flyer_word_count`): runs of characters separated by spaces, tabs or line breaks. Never change one without the other. Approve stays off until `lstFlyerReady()`.
- The flyer version is written by AI (`lstFlyerWrite`) from the saved description. It is a rewrite, never a truncation, and uses only facts in the description. Its voice and word rules are sliced out of the Listing Description Writer's own prompt (`_lstFlyerVoice`), so never restate them elsewhere. An answer over 200 words, with a banned word or a long dash, or with wording about who should live there, is sent back with the reason, up to three tries; nothing is saved unless a try passes, and a failure is said on screen and leaves approval off. **Fair housing: flyer copy describes the residence, the location and how it lives, never the buyer.** The buyer personas steer which features lead and must never appear in the copy. `lstFlyerIssues()` is the screen for this; it also runs on what an agent types and shows what it finds.
- Fair housing covers the FULL description too (Marc, Oct 11, 2026; a description was approved with "the first-time buyer" in it). The Listing Description Writer's prompt (`LD_SYSTEM`) carries the same rule as the flyer prompt, its NEVER use list is FORWARD's full list (the same words as `LST_FLYER_BANNED`; change one, change the other), and its example description must pass `lstFlyerIssues()`. `lstWhoIssues(text)` is the who-should-live-there half of `lstFlyerIssues()`, run on both texts. **Approve for marketing stays off while either text has such a phrase** (`lstApprWhoBlocked()`), and `lstApprove()` refuses by itself, before any request. The listing and the writer quote the phrase in red. The OS never clears an approval by itself: text approved before the check shows a red line under its approval and is cleared the usual way, when the corrected text is saved. The check lives in the browser only; the database does not enforce it. It is a pattern list (`LST_FLYER_WHO_RX`), so it catches the common phrasings and not every one: never describe it to an agent as a guarantee.
- The branded PDF (`lstApprBuildPdf`, `lstApprMakePdf`) is CLIENT FACING (Marc, Oct 9, 2026): it carries the address, the listing agent's name and the description, and nothing about the approval (no approved-by, no approved date, no "approved for marketing"). It is made in the browser on approval and stored in the PUBLIC storage folder `listing-description-pdfs` (PDF only, the app may add files and nothing else). One file per approval, under a new folder name every time, never replaced. The app opens the public address with no key before recording it with `set_listing_description_pdf`, and only then tells Concierge. A PDF failure never undoes an approval: `pdf_url` stays null, the listing says the PDF was NOT produced and offers Make the PDF, and Concierge is still told without it.
- Telling Concierge about an approval: the browser calls the Netlify function `notify-description-approved` with only the listing id. The function reads the approval and the listing from the database itself and posts the JSON to a Zapier catch hook whose address is the Netlify environment variable `ZAPIER_DESCRIPTION_APPROVED_HOOK`. **The hook address must never appear in `index.html` or in any answer to the browser.** The JSON shape (`buildPayload` in that file) is what the Command Center's Zap is built against: do not change a key without asking Marc. Since the flyer and PDF were added the message also carries `flyer_content` (always, empty for an older approval) and, only when the PDF was produced, `pdf_url` and `pdf_filename` (the last part of the PDF's address). A failed message never undoes an approval: the listing says Concierge has NOT been notified, offers Notify Concierge, and the attempt is recorded in `os_settings` under `ld_approval_notice:<listing id>`.
- "Editing now" marker (Oct 9, 2026): while the Listing Description Writer is open on a listing that already has a saved description, the app keeps one row for the listing in `listing_description_editing` (SQL in `sql/2026-10-09_listing_description_editing.sql`). **The Command Center reads this table and warns Concierge, so its four columns (`property_id`, `editor`, `started_at`, `last_active_at`) are a fixed contract: never rename or retype them without asking Marc.** The app can only READ the table; it calls `listing_description_editing_start`, `_touch` and `_stop` (each takes `p_property_id`, `p_editor`). The row is written when the writer opens, refreshed about every 60 seconds only while the tab is visible, and removed on save, on leaving the writer, on switching listing and on tab close (best effort). The Command Center ignores a row whose `last_active_at` is more than 3 minutes old, so never rely on the removal. No row for a listing with no saved description. It is a courtesy signal: a failed marker call must never block, slow or warn the agent. Log it to the console and carry on (`_ldEditCall`).
- Listing presentations (Marc, Oct 12, 2026): the browser holds NO Canva link and never names a file or design. `lpresDownload()` sends only the signed-in agent's name to the backend (`GET /api/listing-presentation?agent=`), which checks its own record for that agent and returns a 5-minute link to that agent's PDF; the app opens it only if the answer names the same agent. The backend exports each deck from Canva every hour and on Marc's Refresh from Canva, and stores a PDF only after checking the first agent contact in it is that agent's (forward-os-backend `listing_presentations.py`, `canva_link.py`). Logins not in `LISTING_PRESENTATION_AGENTS` (Operations, Concierge) have no deck. Never put a Canva edit link back: Canva refuses anyone not signed in to the team account. Marc's Refresh from Canva lives in the listing's own Listing Presentation tool (Oct 13, 2026; until then only in the old Listing Package panel, which the navigation no longer opens).
- Meet Your Advisor (Marc, Oct 13, 2026; called Seller Guide before) is the agent's two-page intro and bio sent before a listing appointment, one PDF per agent in `seller-guides/` (`SELLER_GUIDES`, `sellerGuideUrl`; internal names unchanged). The file is downloaded as `<Agent>_Meet_Your_Advisor.pdf`. **On a phone, never link straight to a PDF on the OS's own site:** in the home-screen app it replaces the whole app with no way back. Phones open it in the in-app viewer (`pdfViewOpen`, `fosIsPhone()`), which has Back and Share; the viewer's markup stays at the top level of `#app`, because beside the other modals it is not drawn on a phone.
- Buyer offers live in the `buyer_offers` table, one row per offer. New offers are sent as insert-ignore-duplicates with an id made on the device; changes are a PATCH limited to rows that are not removed; nothing ever clears `removed_at` and nothing is hard-deleted. Never save offers as one list again.

## Saves must tell the truth

- `fetch()` does not throw on a 404 or 500. Pass every save's answer through `fosOk(res)` (in `index.html`), which throws unless it succeeded.
- Show a success message only after the save went through. On failure, say what was not saved and why (`fosWhy(e)`), and leave the agent's text on screen.
- Never `catch` a failed save with only `console.warn`. A new save gets a case in `ci/save-failure-test.js`.

## No demo output, ever

- No tool may show sample, mock or demo output. A tool that cannot do its job says why and produces nothing. Until Oct 3, 2026 three tools showed made-up output on a device with no AI key.
- The AI key is checked by `fosCheckAiKey()` at sign-in, on page load and on agent switch. It is the only place the key is looked up. `aiKey.state` drives the red notice on every screen.
- Agents cannot add their own key: the key boxes in Settings are shown to Marc only. Never tell an agent to "add your key in Settings".

## Automatic checks on every pull request

GitHub runs `.github/workflows/pr-checks.yml` on every PR to `main` or `staging`:

- `ci/static-checks.js`: scripts parse, the `#app` template compiles, every name the template uses is returned from `setup()` and declared, `index.html` did not shrink, CHANGELOG is well formed.
- `ci/mount-check.js`: opens the real app in headless Chromium, logged out and as every login, and opens every view. All network calls are intercepted; it never touches production.

- `ci/offers-test.js`: the Offer Tracker against a made-up `buyer_offers` table, as several devices at once. A failed save is shown, a retry never duplicates, a removed offer never comes back.
- `ci/save-failure-test.js`: runs each save with the cloud working and with every write failing. A success message may appear only when the save went through. A tool's PDF is filed on the listing under a new name each time, a refusal by the PDF store is said with its reason, a text-only save files nothing, and the listing lists its PDFs newest first, opens the exact file, never shows another listing's, and says when the list cannot be loaded.
- `ci/meeting-prep-test.js`: a Meeting Prep brief says when online research did not run and research slower than 30 seconds is still used. One case waits 33 seconds on purpose.
- `ci/ai-key-test.js`: the AI key check at sign-in. No notice when a key is there; a red notice on every screen when it is not; with no key the tools produce nothing and say why.
- `ci/cma-builder-test.js`: the CMA Builder (`cma-tool.html`). The newest saved CMA for a listing opens and an empty one never hides one with properties in it; orange review boxes clear once clicked or changed and the count equals the boxes on the page; Back to Listing returns to the listing. An imported comp gets its monthly fee from the MLS sheet (HOA fee plus condo fee, the same sum the subject uses), a blank comp fee gets no HOA adjustment while a typed 0 is adjusted in full, and a closed sale with a blank fee is orange until a number is typed. On a computer (1280, 1440 and 1920 wide) the comps tables fit their cards with no sideways scroll, no cut header and no box outside its cell; orange boxes have a Confirm button. A notice names any closed sale whose HOA adjustment is more than 5% of its sale price, and showing it changes no value. A garage count above 4 is orange until confirmed; a blank Garage box on a closed sale gets no parking adjustment and is orange until a number is typed; a notice names any closed sale whose total adjustment is more than 15% of its sale price; the listing's own garage is read from its MLS Data line. A new CMA values condition as a percent of sale price, checked against an independent calculation, with the key on screen and on the PDF inside the page; a CMA saved before Oct 6, 2026 keeps its dollar grades, letters and numbers. A copy of the CMA is kept under Earlier Versions when a PDF goes out, before Reset and before an earlier version is opened; Reset from a listing deletes nothing and a teammate's older draft does not reopen over it; a kept copy is never changed. Save to Listing stores the CMA PDF on the listing under a new name each press, saves the summary with it, says a refusal out loud, and sends nothing to the old upload service. A 4.3 MB file says to expect about 2 minutes, is not Almost there at 30 seconds, and past the guess says Still reading with a bar that never fills. With more properties ticked than a section holds, nothing is added until the agent unticks enough, what the agent kept is what goes in, and a property already in the CMA takes no room; a listing address with no comma before the city is split into street, city and state and marked to check.
- `ci/net-sheet-listing-test.js`: three made-up listings, each with its own MLS Data. A net sheet left open on one listing never shows on the next; one click opens the form with that listing's address, list price and HOA fee; typed figures are kept on reopen; the standalone net sheet opens blank after a listing's. A market written out in full (Maryland, Virginia) is read as MD and VA.
